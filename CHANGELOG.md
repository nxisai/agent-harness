# Changelog

## 0.15.2

No change to the package's code. This release is about where it is published from.

### Changed

- **Published to npm from this repository, with provenance.** Each version is now published by this repository's Publish workflow (`.github/workflows/publish.yml`), using npm trusted publishing with `--provenance`, after a maintainer approves it in the `npm` environment. On npm, the version links to the run that built it, and its `repository.url`, `homepage` and `bugs` name `github.com/nxisai/agent-harness`. Earlier versions named a repository that isn't public. Before publishing, the workflow checks that the tag matches `package.json`, that `repository.url` names this repository, that nothing internal is in the tree or in `dist/`, and that typecheck, build and tests pass on Node 20 and 22. CONTRIBUTING.md, "Releases", covers the whole flow and how to verify a version.
- **Checked for anything internal before it ships.** `scripts/check-public.mjs` fails on references to private repositories, issue or pull request references, internal or tunnel hosts, connection strings, non-example email addresses, and a list of internal names, kept as hashes so the file doesn't publish them. It runs on the tree this repository receives, on the npm build (`dist/`) and on the CDN build (`dist-cdn/`). Usage: `node scripts/check-public.mjs <file|dir|.tar.gz>...`.
- **Placeholders in the bench and the tests.** `bench/proxy/.env.example` uses `your-tunnel.example` for the tunnel host. Test fixtures use reserved example domains for email addresses and a business's site.

## 0.15.1

### Fixed

- **A turn no longer ends on result cards with nothing said.** Asked "What are your hours?", the assistant listed the site's record types, drew them as twelve cards (BreadcrumbList 16, Plumber 16, …) and stopped: the harness ran one tool a turn and ended the turn on its results, so the model never saw what came back, never searched, and never answered. A search that did run ended the same way, with location cards and no sentence; the second request a page made in that turn was the recommendation, whose words are not shown.
  - **A read is a step.** Once a read's results are drawn, the model is asked again with them: it calls the next read it needs (`nxis_list_types` to pick a type, then `nxis_query`) or answers in a sentence or two from the results, under the cards. The cards stay.
  - **A type listing is never the answer.** Its result reaches the model as "the kinds of records this site has. To answer, search them with nxis_query next, unless the visitor asked what kinds there are", and `nxis_list_types`'s description says it is a step before `nxis_query`.
  - **Bounded.** At most three reads a turn (`MAX_STEPS`, or the guardrails' `tools.maxPerTurn` when lower); after the last, the model is offered no tools and can only answer. The same read isn't run twice. A reply with neither words nor a call is asked for once more, with no tools and an instruction to answer that is added to the read's result for that request only and never kept; then the cards stand with "Here's what I found." (or "I couldn't find that here." after no records, or after only a type listing). Each is one more completion within the guardrails' step and token budgets. A stop during the answer keeps the cards and drops the unfinished answer.
  - **The answer has the facts.** The model reads back up to 4,000 characters of a result (`RESULT_CHARS`) instead of 400, enough for a page of records' hours.
  - **Still a step to a model proxy.** Every request after the first in a turn ends on the read's result, in its data block, so a proxy counts it as a step of the turn, not as a new message from the visitor. See docs/remote-providers.md.
  - A read the visitor confirmed, or one that waited on a field, is answered the same way once it runs; if the visitor sends another message first, that answer is dropped and the new turn goes on.
  - **Sizes.** The ui page-load budget's margin rises from 17,698 to 18,588 B (+890 B) for the answer step, its bounds, the nudge and the type listing's wording.

## 0.15.0

### Added

- **Handoff targets from A2A agent cards.** With NxisAI's relay, `handoff: { relay }` is enough: the harness reads the site's specialists as agent cards from `<edge>/v1/s/<site>/agents` (beside `…/handoff`), the first time the targets are read and never on page load, keeps them 30 s and reads them again with their ETag. Only a card whose `url` is the relay's own endpoint for the target it names is trusted. The handoff tool's description gives each card's description and skills, and every turn describes the tools from the targets listed now, so a paused specialist is gone from the next turn after a refresh. A page's `targets` work as before, merged with the cards, and a target can name its own card (`card: '/a2a/desk/agent-card.json'`, on the relay's origin) for a self-deployed relay. The card reading is a lazy chunk (1.8 KB gzip); the ui page-load graph is 20 B smaller than before, with no margin change. With `discover="false"`, the handoff tools are now registered at the first open too. See docs/handoff.md.
- **A contained preview: `contained`.** `<nxis-agent contained>` draws the same launcher and window as window mode, with the same markup, CSS, sizes, shadow, header buttons and footer, inside the host element's box instead of fixed to the viewport: 20px from the box's bottom right, at `--window-w` × `--window-h`, capped to the box less 16px a side. The launcher opens it, ✕ closes it back to the launcher (focus returns to the launcher), and `auto-open` starts it open without taking focus from the page. The header's expand button fills the box, with the conversations in a drawer as in a window, and shrinks back; the choice isn't stored. The `mode` attribute, a stored mode and the 520px narrow-viewport rule don't apply. Messages are off: the input and send button are disabled, the placeholder reads "Preview only: messages are off", and the suggestion chips are drawn as a visitor sees them but send nothing; `allow-input` (or `allowInput`) turns them on. It fetches nothing: discovery and site actions are off, `preload` is `none`, and opening loads only a `modelProvider` the host supplied, never the on-device model. Conversations aren't read from or written to storage, and nothing left pending on another page is resumed. Nothing is drawn outside the box. The host gives the element its size. Also a `contained` property. See "Previewing the chat" in the README.
- **Opening and closing from the page: `close()`, `isOpen` and `nxis-agent-toggle`.** `agent.close()` closes the window to the launcher as ✕ does, in every mode, and does nothing when already closed; `agent.isOpen` says whether the window is showing; and the element fires `nxis-agent-toggle` (`detail: { open }`, bubbling and composed) once for each change, from the launcher, ✕, `open()`, `close()` or `auto-open`. ✕ (and `close()`) now move focus that was inside the agent to the launcher in every mode, rather than leaving it on the hidden button; focus elsewhere on the page stays put.
- **Event cards in the chat, as the NxisAI Hub draws them.** Events (`Event`, `Festival`, `ConferenceEvent` and schema.org's other event types) now draw as their own card rather than as generic records: a date tile, the name and its kind, and a pill with the status (Cancelled, Postponed, Rescheduled, Moved online, Past) or the access (Free, a price or "From $48", Sold out, "On sale Jun 1"); then when, in the event's own time zone with the zone named when it differs from the visitor's, where (the venue and city, "Online", or both), the date a rescheduled event moved from, who runs it and who's on (a venue or person the site holds asks for its card); then Get tickets or Register, Add to calendar and Directions; then its days or sessions, three until "Show all". In a list they are rows, grouped under "Events", upcoming soonest first and past ones last. Every value comes from the record: one with no dates, place or offers shows none, and no offers is never "Free".
  - **Get tickets** opens the site's ticket form on its own page (`nxis:targetKind: selfPage`, `nxis:pageUrl`): on that page the form starts in the chat, as a handoff link starts it; on another page of the site the visitor is handed to it (`?nxis_handoff=…&nxis_report=…`) and the form opens in the same conversation there. With no page for the form, the first offer on sale opens its `url`; with neither, there is no button. Taps report `purchase_start` or `register_start` to the site's `nxis_track_site_action`, with the action and its token; only the site's own confirmation counts as a conversion.
  - **Add to calendar** opens the site's own https `.ics`, else the file the site's MCP server builds from the record, `<endpoint without /mcp>/ics/<base64url of the @id>.ics`, for records that came from that server and only when a browser can reach it without a key (`ConnectResult.calendar`). **Directions** opens a map for a venue with a street address.
  - The renderer spec is synced from the NxisAI MCP server: events are phase 1, with the `happening` words the cards use, and a `CourseInstance` still waits for a later phase. `eventCard`, `eventAccess`, `eventFacts`, `arrangeEvents`, `calendarUrl` and `recordKey` are exported from the main entry, and `emitEventSurface` and `emitEventsSurface` from `./a2ui`, whose `emitResultsSurface` draws events too.
  - **Sizes.** The cards, the event model and their A2UI surfaces are a chunk of their own, 8,320 B gzip under a new `events` budget of 8,704 B, loaded with the first result that is an event. The ui page-load budget's margin rises from 11,791 to 13,733 B (+1,942 B) for what has to be there before that: the `happening` block of the spec, the answer view's hooks for events, loading the chunk and handing it the element's links, reports and form start, the calendar address from discovery, and the handoff link's token. The chunk shares the entity reader and the spec with the page-load bundle, which esbuild splits into a chunk of their own.
- **A CDN build.** `npm run build:cdn` writes `dist-cdn/harness/<version>/`: `ui.js` (the element, bundled, with each lazy part as a content-hashed chunk beside it), a self-contained `proxy.js` (`createProxyProvider`), and `manifest.json` with every file's Subresource Integrity hash. A `harness/<major>.<minor>/` alias re-exports the latest patch. `upload.json` plans the upload to S3 behind CloudFront (each object's `Content-Type` and `Cache-Control` as metadata, the version write-once, the alias last), and `scripts/publish-cdn.mjs` carries it out. `npm run size:cdn` checks the build file for file against the size budgets, which gain `lazyChunk` (4,096 B, for the sources and feedback chunks) and `cdnProxy` (1,536 B). `npm run smoke:cdn` loads it in a plain page and runs one turn. See "Without a bundler" in the README.

### Changed

- **A page's search or filter form is a read, and the site's records come first.** A site form recorded as `method="get"` now becomes a read-only tool (`readOnlyHint: true`) when it is a `SearchAction`, or when no script handles it and it asks for nothing a sent form would (an email, a phone number, a name, a message, a file): a form that names no method is recorded as GET too, and may still send. It runs with no confirmation card and no send wording ("Looking that up."), and what it does is open its results page with the filled-in query string, from its observed URL (`nxis:observedUrl`, now read) or its page, keeping the conversation. A GET form a script handles is filled on its page, as before, without a confirmation. `readsOnly`, `resultsUrl`, `pageTitle` and `formNoun` are exported from `./tools`.
  - **The records first.** `nxis_query`'s description and the default system prompt tell the model to search the site's records for questions that find, list or show things (what's on, events, products, places), and to use a page form only for what the records can't do. A read-only form's description says the same. `nxis_query` takes `when` (today, tonight, tomorrow, this weekend, next weekend, this week, next week, this month, next month, or a month such as July), or `from` and `to` as `YYYY-MM-DD`, read on the visitor's clock; its description gives today's date. The server compares only numbers, so a dated search reads records soonest first by `startDate` (up to three pages of 100) and keeps those on during that time, including one that began before it and ends during or after it. The result says the days it searched (`date_range`). This is a lazy chunk, loaded by the first search that names a time.
  - **Names, not ids or paths.** A form is "the quote form" where its name reads as one, else "the form": never its HTML id ("this filters"). A card sends "to McGreevy Plumbing" only when the form names who it is for, else "for you". A form's page is named by its page record's title, or the open page's own, never by a path segment; with neither known the card shows the site's name. Leaving for a form's page says "Opening the form’s own page to send it from there." `withoutSiteSuffix` also drops the `_2` a repeated name gets. The ui page-load margin rises by 1,687 B.
- **A spend refusal from the model proxy reads as a pause.** `spend/cap` (the site's monthly spend cap reached) and `spend/credits` (the organization's credits used up) now say "The assistant isn't available right now. Please try again later.", as `input/lockdown` does. They used to fall through to "I can't help with that here."

### Fixed

- **One form is one tool, even when its fields differ by page.** Wrenfield's pass form (`#pass-form`, posting to `/api/checkout` with a hidden `event` and one `qty_{tier}` per ticket tier) showed in the tools menu as six site-wide tools, "Pass form" and "Pass form anywhere 2" to "6", one per event family's tiers. It is now one.
  - **Grouped by where it submits.** Site actions with the same name are one tool when they submit to the same endpoint (`urlTemplate`, else `nxis:observedUrl`) with the same method; only a form with no endpoint is still told apart by its field list. The merged schema requires only what every page requires, and a field's limits widen to what any page allows.
  - **Chosen by the form's own constant.** `parseAction` reads `nxis:fixedInput` (an object or a list) into `NxisAction['nxis:fixedInput']`, apart from `input`, and a constant with a different value on each page (the hidden `event`) chooses between them. It is never sent: the page's form already holds it. The tool carries `ai.nxis/chooserFixed`, and `chooserIsFixed()` reads it.
  - **Each event by name.** A constant, or a value that reads as a code, is offered by its page record's title without the site's name ("Low Light Pittsburgh: Furnace Songs, Fri, Sep 10"), else the code in words ("Low Light Pittsburgh, Sep 10, 2027"), never its URL. The site's page records are now read before its tools are built, so the titles are there. A call naming the code itself still picks its event. The added `target` choice is named by page title too, where there is one.
  - **Checked against the chosen event's own fields.** Once a call says which event, `siteCallFit()` checks it against that event's fields before anything is confirmed: a tier it doesn't sell, or more than its limit, is turned down with that event's tiers and limits ("\"Weekend passes\" isn't available for … It offers General passes (up to 8) and Front Rows passes (up to 4).") for the visitor, and with the field names for the model, which may try once more, since nothing ran. The card then asks and shows only that event's fields, and only those are carried to its page. A call that comes some other way is checked as it runs.
  - **Names without the registry's suffix.** The card reads "Get passes for Low Light Pittsburgh: Furnace Songs, Fri, Sep 10." The description fits the whole form ("The site's pass form, on the page of each event."), not one event's. The thread's tool headings, "Running …", "One more thing for …", result and detail titles and the tools menu drop `_anywhere` and any number after it. A page is no longer named after a quantity's "0" or an event code.
  - **Sizes.** The ui page-load budget's margin rises by 2,240 B for the grouping, the chooser, the event names, the per-event check and its wording.
- **A second copy of the harness on a page no longer throws.** Another version, or the CDN build beside the npm build in a site's bundle, failed as it loaded, because `@a2ui/lit` defines its elements without checking for a name already taken. The first copy's elements now stay, and the registry's own `define` is restored straight after. The ui page-load budget's margin rises from 11,221 to 11,274 B (+53 B) for it.

## 0.14.0

### Added

- **Remote guardrails, part 6: end to end.** A test runs the page against a proxy written to the contract, with a scripted model: a policy change on the proxy applies to its next request with no page deploy, the page picks up the new version from the answer and enforces it too; if the copy can't be fetched, the page runs on the built-in defaults and the proxy still refuses; with a held prompt, the page sends none. [docs/guardrails-policy.md](docs/guardrails-policy.md) has the whole contract. The `agent-model-proxy` skill writes the proxy, for Netlify, Vercel, Cloudflare and Docker.
- **Remote guardrails, part 5: `guardrails-src`.** `<nxis-agent guardrails-src="/api/agent">` reads the model proxy's guardrails policy: the guardrails load a chunk of their own (2.1 KB gzip, under a new 2.2 KB budget) only when the attribute is set, fetch the copy, cache it with its ETag in `localStorage`, and merge it over the page's configuration tighten-only. Each completion sends the version held (`Nxis-Guardrails-Version`); when the proxy holds another, the copy is fetched again. If it can't be fetched or read, the built-in defaults apply; a copy that loaded is kept if a later fetch fails.
  - **The proxy's refusals** (`{ error, refusal: { stage, rule, action, severity } }` on a non-2xx answer, or in a 2xx body) are said with the page's own message for that rule and raised as the same `nxis-guardrail` event and `onDecision` call. Only those four fields, in the shapes the guardrails use, are kept.
  - **`createProxyProvider`** sends back the conversation id the endpoint issued (`Nxis-Conversation`) and the policy version, only once there is one of each; reports `completion.guardrails` (`version`, `refusal`). `CompletionRequest.guardrails` and `Completion.guardrails` are typed. With no guardrails at the endpoint, requests and failures are as before.
  - **The guardrails chunk budget rises from 8,213 to 8,447 B gzip (+234 B)**: loading the policy chunk, the version on each completion, and saying a proxy's refusal. The policy chunk shares the guardrails' `settingsFor` and `glob` (`tightenWith` in `policy-core.ts`), since a shared chunk between the two would have cost about 600 B more. The ui page-load graph is unchanged.
- **Remote guardrails, part 4: a system prompt the proxy holds.** When the policy copy says `prompt: 'proxy'`, the guardrails send a remote model no system message and no canary line: the proxy uses its own prompt and makes and checks its own canary. An on-device model still gets the page's prompt. A runtime's `remote` (`RemotePolicy`, exported as a type) is the hook: the policy merged tighten-only on every read of the configuration, the version held, and whether the prompt is held. **The guardrails chunk budget rises from 8,192 to 8,213 B gzip (+21 B)**, the minimum for this; the page-load graph grows by 1 B.
- **Remote guardrails, part 1: the policy document.** A versioned, declarative JSON document (`schema: 1`) of what a site's guardrails enforce: the preset, input, tool, model, conversation and output limits, tool allow and deny lists and tiers, link origins, overrides, the kill switch, and an optional system prompt the proxy holds. `@nxisai/agent-harness/policy` exports `parsePolicy` (refuses a malformed document whole, with a `PolicyError` naming the field), `browserCopy` (the document without its system prompt, with `prompt: 'proxy'` when the proxy holds one) and `tighten(config, policy)`, the merge the page uses: **tighten-only**. Numbers take the lower of the page's and the policy's; strict wins; deny lists add up; an allowlist only narrows; a policy's tier is a floor (the new `policy/tier` rule asks for the confirmation and bound approval where it raises a tool to `high` or `critical`); link origins only narrow (the new `output.onlyOrigins`); overrides never reach the checks that can't be turned off; a lock is never lifted. The types are re-exported from `@nxisai/agent-harness/guardrails`. [docs/guardrails-policy.md](docs/guardrails-policy.md) documents the document. The guardrails chunk grows by 37 B gzip (`onlyOrigins`); the policy module itself isn't in it.

## 0.13.0

### Added

- **Inline citations on a remote answer.** A handoff target's answer now marks each claim with a small numbered button after it (**Source 1**, **Source 2**…; several for a claim with several sources), and lists its sources in a **Sources** section attached to the bubble: one numbered row per record, with its title, what it is and the passage cited ("How-to · steps 3–5", "FAQ", "Video · 2:14 · Removing the cover") and an external-link icon ([Heroicons](https://heroicons.com) `arrow-top-right-on-square`). Numbers follow the order sources first appear in the text; a source no claim cites is listed after, unmarked; a one-source answer is numbered too. A marker moves focus to its row and highlights it. A row opens its source as the card's Read or Watch did (this page in place, another page of the site in this tab with the conversation kept, another origin in a new tab), and now asks the guardrails' navigation check first. A video or a clip and a profile are still drawn as their cards under the bubble, wearing their number; an article, an FAQ, a how-to and a page are their row alone, and a record already drawn in the conversation is listed rather than drawn again. The list and the markers are drawn in the bubble's own colours. They load as a chunk of their own (3.1 KB gzip) with the first answer that has cards; the page-load graph is unchanged (+3 B).
  - **The `answer` part gains `claims`** (optional): the text each claim is drawn as in the reply, by claim index, which is where the page puts the markers. A cite may name its card with `record` when its `id` is a passage's own. A target that sends no `claims` gets the Sources list and no markers. The envelope declares `ui: { cards: 2, feedback: 1 }`. `HandoffAnswer.claims` and `AnswerCite.record` are typed.
- **Guardrails, part 6: the adversarial bench and the docs**. `bench/cases/guardrails/` covers prompt override, indirect injection (a tool result, the page, a hand-back), tool misuse, approval bypass and replay, recursion and cost loops, exfiltration (a URL, a summary, a reply) and system-prompt extraction, each with benign controls, in English and Spanish, German or French. `node bench/runner/guardrails.mjs` runs them offline after a build, against the headless harness with a scripted worst-case model and instrumented tools: no model, no spend. Each case is recorded as a violation, no violation or inconclusive, with errors counted apart. The README has a Guardrails section: the API, and the defaults rule by rule with the OWASP cheat-sheet section for each.
- **Guardrails, part 5: the host API**. Import the types from `@nxisai/agent-harness/guardrails` (`GuardrailsConfig`, `GuardrailRule`, `Verdict`, `GuardrailDecision`, …).
  - **`rules`**: a host's own checks for the `input`, `context`, `tool`, `output` or `handoff` stage, synchronous or async, run in order after the built-in rules. They can only tighten: `flag`, `confirm` (a tool call then needs the visitor's approval) or `block`; `allow` lets the built-in decision stand. A `context` rule that blocks keeps that untrusted text from the model.
  - **`classifier`**: an optional model-based guard (a host's Prompt Guard endpoint, say), asked at the input and output stages. None ships.
  - A rule or classifier that throws or takes over 5 s **fails closed** at the `tool` and `handoff` stages and **open, with an event,** at the others.
  - **`overrides`**: `{ 'input/injection-phrases': 'off' }` loosens a built-in rule by name, logged once per page with `console.warn`. The approval, policy, lockdown and list checks can't be turned off.
  - **`preset: 'strict'`**, or `guardrails="strict"` on the element: input screening blocks instead of flagging, `medium` tools are confirmed too, remote MCP tools are off unless `tools.allow` lists them, and the caps are tighter (2,000-character messages, 6 sends and 15 tool calls a minute, 2 calls a turn, 15 s per call, 4,000-character replies, one-minute approvals).
  - **The kill switch**: `agent.guardrails.lockdown(reason, scope?)` (or `lockdown()` on a runtime) turns tools off (`'tools'`) or the whole agent, remote sends included (`'agent'`), at once, even before the chunk has loaded; `agent.guardrails.locked = null` lifts it. A host's remote config can set `locked` directly.
  - **The element property**: `agent.guardrails = { … }`, beside `modelProvider` and `handoff`, applies from the next check, for every agent the element runs; it keeps the conversation's counters and approvals. **Headless**, `new AgentHarness({ guardrails })` takes the same object, or a runtime from `createGuardrails(config)` for agents and custom engines to share.
- **Guardrails, part 4: handoff**. Secret-looking text in the model's `reason` and `summary` for `transfer_to_agent` or `talk_to_a_person` is replaced with `[withheld]` before the visitor sees the summary, and so before it leaves the page (`handoff.screenSummary`, on by default; turned off, the argument check refuses the call instead). A handoff is always `critical` and confirmed, whatever tier a host gives it, so the transcript is sent only when the relay asks for it and after the visitor's Send. What comes back (a hand-back's note and references) is untrusted data, screened as it reaches the model, and a remote agent's reply can't make a local tool run outside the tier and confirmation rules.
- **Guardrails, part 3: input and output**.
  - **Input**: a message over 4,000 characters (`input.maxLength`) is refused before the model, and so is an eleventh send in a minute in one conversation (`input.sendsPerMinute`), with a friendly line. Both apply to a message for a remote agent too. **Screening is a signal**: on an NFKC-normalised copy (accents and invisible characters dropped), and on what Base64 and hex in it decode to, zero-width, bidi and Unicode tag characters and injection phrases (overriding instructions, revealing the prompt; in English, Spanish, French and German) are flagged, and a flagged send counts twice towards the rate. The visitor's text is never changed. Untrusted data is screened the same way as it reaches the model (`context/injection-phrases`), once per message.
  - **The canary**: a per-conversation marker in the system prompt. A reply or a tool call that contains it, however it is spaced or cased, is blocked ("I can't share that.") with a `critical` event, and it never streams onto the screen.
  - **Output**: a reply that leaks a key or a token is blocked; the host's `output.redact` patterns are replaced with `[redacted]`; a reply over 8,000 characters (`output.maxLength`) is cut; a URL with a long encoded or high-entropy query value or fragment is flagged as possible exfiltration. Replies are still drawn as text, never HTML (a regression test now says so).
  - **Navigation follows `link-origins`**: `open_page` to an origin that isn't the page's own or listed needs the visitor's confirmation (and an approval for that call), and a card's link elsewhere asks first ("Open elsewhere.example? It's another site, not this one."). Anything but http(s) never opens. Headless, `output.linkOrigins` lists the origins.
- **Guardrails, part 2: tools**. Least privilege and a human in the loop, decided by code, never by the model:
  - **Risk tiers**: a read from the page's own registry is `low`; a read from a remote MCP server or the site, or one declaring `untrustedContentHint`, `medium`; a write `high`; `destructiveHint`, `consequentialHint`, or a write that pays or changes an account (`checkout`, `refund`, `delete_account`, …) `critical`; **an unannotated or unknown tool `high`**. The host's `tools.tier` wins. Only `low` runs unreviewed; `medium` runs and is logged; `high` and `critical` are confirmed. A tier that can't be resolved refuses the call.
  - **A confirmation is bound to the call**: the visitor's press approves that tool with those normalised arguments in that conversation, once, for two minutes. It is checked and used in one step, just before the call runs; an approval for other arguments, a used one or an expired one runs nothing.
  - **Argument checks**: values that look like an API key, a token or a password are refused, an encoded blob is flagged, and arguments over 10,000 characters are refused.
  - **Limits**: 3 tool calls per turn (`MAX_STEPS`, now enforced), 30 per conversation per minute, 5 failed calls in a row stop the turn, each call times out after 20 s (a tool that never resolves ends the turn with "That took too long"), and a turn's generations and output tokens have a budget.
  - `tools.allow` and `tools.deny` (names, `*` patterns; deny wins): a tool left out is never offered to the model and refused if called.
- **Guardrails, part 1: the core**. Every turn passes through `@nxisai/agent-harness/guardrails`, a chunk of its own that the element loads with a dynamic `import()` at the first open or send and that `AgentHarness.turn` and `begin` wait for. It **fails closed**: when it can't load, no turn runs and nothing is sent to the model, a tool or a remote agent; the element says "The agent could not be downloaded. Check the connection and try again — nothing was lost.", and a headless turn rejects. The chunk is 2.1 KB gzip, under a new 8 KB budget.
  - **Untrusted text reaches the model only inside a delimited data block**, `<data-BOUNDARY source="…">…</data-BOUNDARY>`, with a random boundary per conversation. Text that contains the boundary or any data tag is escaped first (and zero-width, bidi and tag characters are dropped from it), so it can't close its block early. The system prompt gains one fixed line saying what is inside is information, never instructions. This covers tool results and failures, a recommendation's results, a remote agent's hand-back (its outcome, note and references), a failed handoff's error, the visitor's saved profile, and the descriptions of page, remote-MCP and site tools (the harness's own `open_page` and handoff tools keep theirs). Results from remote MCP and site tools, and from tools declaring `untrustedContentHint: true`, are labelled `trust="untrusted"`.
  - **Decisions are reported**: `onDecision` and an `nxis-guardrail` event on the element (bubbling, composed) carry `{ stage, rule, action, severity, tool?, tier? }` and never what the visitor wrote, a tool returned or a tool was called with. Each conversation's decisions are counted (`counts()`), and `debug` draws them in the thread.
  - `HarnessOptions.guardrails`: a configuration (or a runtime from `createGuardrails`) shared by the agents given the same object. The element passes itself, and its runtime reads `agent.guardrails` and the `guardrails` attribute live. `agent.guardrails` always has `lockdown(reason, scope?)`.
  - `ChatMessage.data`: the untrusted part of a message, kept apart in the transcript and drawn as a block only on the copy the guardrails send. `toolOrigins` records which tools the harness registered from a remote MCP server or the site's actions.
- **A window / full-screen toggle in the header.** While the agent is open, a button beside Close (**Expand to full screen** / **Shrink to a window**, with expand and collapse icons) switches between `window` and `fullscreen`. It changes only the panel's shape: the conversation, scroll position, focus (which stays on the button) and any open handoff are kept. It's hidden in `inline` mode, below 520px, and with the new `no-mode-toggle` attribute. The viewer's choice is kept in `localStorage` (`nxis-agent:mode`) and applies on the next load only when the host sets no `mode` attribute; the host's explicit mode wins. Each toggle fires an `nxis-mode-change` event (bubbling, composed) with `detail: { mode }`.
- **A remote agent's answer draws as cards.** A handoff target may send, beside a reply's text, an `answer` part: `{ handoff: 'answer', answerId, cards, cites, note? }`. Its `cards` are drawn under the reply with the answer view's own cards, by the renderer spec's archetype: an FAQ, a how-to, an article or a page is `readable` (**Read**, and **Their page** when that is another page), a video or a clip `media` (**Watch**, at the clip's time on YouTube and Vimeo, or in the chat with `media="play"` when the player may play it), a profile `profile` and a product or a service `offerable` (**Their page**). None carries an action CTA. A card's `focus` shows the passage it cites ("2:14 · Removing the cover"); `citation: 'page'` is labelled **From the page**, with one **Open the page** link; a record already drawn in the conversation is a compact row, not a second card; `note` (the language note) is drawn above the reply. `readAnswer()` and the `HandoffAnswer`, `CardRecord`, `CardFocus` and `AnswerCite` types are exported from the package root, and the `message` handoff event carries `answer`.
- **Links in a remote reply open**, bare or as Markdown, when their origin is the page's own or one listed in the new `link-origins` attribute (https only for another origin, in a new tab with no referrer). Anything else stays as text. A link to another page of the site keeps the conversation.
- The handoff envelope declares what the page draws: `ui: { cards: 1 }` (`HANDOFF_UI`). It isn't listed in `consent.shared`.
- **👍 and 👎 on a remote agent's answers.** Each answer with an `answerId` gets two toggle buttons, **Helpful** and **Not helpful** (`[data-feedback="up|down"]`, in a group named "Was this answer helpful?"). A click sends `{ handoff: 'feedback', answerId, value: 'up' | 'down' }` with `SendMessage` on the same task. It isn't drawn as the visitor's message, never reaches the page's model, and is sent at most once per answer, kept across reloads. The controls are disabled once the task is over. What the target says back is drawn as its reply. The envelope declares `ui: { cards: 1, feedback: 1 }`. `HandoffController.feedback()`, `feedbackMessage()` and `FeedbackValue` are exported. The controls load lazily, with the first answer that has an `answerId`.
- **A cited clip plays from its start.** With `media="play"`, **Watch** on a remote answer's `media` card whose `focus.startOffset` is set starts the docked player that far into the file. Each clip is an item of its own (`fromOffset()`; its id names the time), so two clips of one video each have their own Play and pressed state. Pausing and playing again carries on where it was. A clip's links out to YouTube and Vimeo carry the time (`t=`, `#t=`), from the clip's own link as well as the video's. Embeds are still to come.

- **`nxis-handoff` events.** The element reports each handoff step on itself (bubbling, composed): a state, a remote message with its `answer`, or a hand-back with its outcome, as a `HandoffActivity` (`handoffActivity()` maps a controller event to one). The detail is a copy and never carries the session or its key.
- The model bench records what a remote agent says after a handoff (its text, its `answer` parts' cards and cites, its hand-back) and asserts on it: `remoteMatches`, `remoteExcludes`, `remoteCards`, `remoteCardsFromOneScope` and `handback`. A case with the prompt `(Send)` continues another by pressing Send on its handoff. `npm --prefix bench test` runs the bench's own tests.
- The model bench routes a remote agent's own model calls through its proxy: `--remote-agent "<command>"` starts the agent with `SUPPORT_MODEL_BASE_URL` (`<NAME>_MODEL_BASE_URL` with `--remote-name`) set to the proxy's `/remote/<agent>/<run>` route, which pins each call to the registry model named on `X-Nxis-Model`, uses the proxy's own key, and records it apart. The report gives the remote agent's calls, cost and latency per page model, separately from the page model's.
- **Podcast episodes and series draw as the NxisAI app draws them**. Media items (`PodcastEpisode`, `AudioObject`, …) and series (`PodcastSeries`, `Course`, …) are no longer drawn as Thing. An episode is a row with no initials avatar: its title, "Lantern Hours · Episode 2 · 0:10 · Free", and its lead button always on show. Episodes from several shows are grouped under "Lantern Hours · 2". A lone series draws as its card: the show's art (or a microphone tile), "Podcast · Brackwater Audio · 12 episodes", a badge said from its episodes ("Free", "Free · some for subscribers", "Subscribers"), **Listen to the latest** and Subscribe, then its episodes, each with its own button, three until "Show all episodes". This works in the answer view and in the A2UI surface (`emitMediaSurface`, `emitSeriesSurface`, `showAllMessages`).

A series with no free episode leads with Subscribe to listen. ### Fixed

- **Guardrails: no override can switch off approvals.** `overrides: { 'tool/tier': 'off' }` used to remove the confirmation for `high` and `critical` tools, and with it the bound-approval check that is documented as impossible to turn off, handoffs included. `tool/tier` can no longer be turned off: like `tool/approval`, `tool/policy`, `tool/lockdown`, `input/lockdown` and `tool/not-listed`, an override of it is ignored, and the one-time `console.warn` now says so ("can't be turned off; ignored"). A host's `tools.tier` still re-tiers a tool, but can't take one that code tiers `critical` (destructive, consequential, a payment or an account change) below `high`, so it is always confirmed; a handoff stays `critical`, and its Send card always appears. Only the value `'off'` turns a rule off.
- **Guardrails: a tool name the model invents is refused by `tool/policy`**, with a `critical` event (without the invented name in it), as the README said. The visitor still reads "I picked an unknown tool …". `Guardrails.unknown()` does it for custom engines. The README's Guardrails section now also lists the strict preset's limits for tool calls a minute (15), failed calls in a row (3), argument size (4,000 characters), generations (6) and output tokens (8,000) a turn; the `output/redact`, `tool/not-listed`, `tool/lockdown` and `input/lockdown` rules; what a rule's `confirm` does at each stage; that `debug` draws decisions in the thread; and that setting `agent.guardrails` merges shallowly and `null` resets it. The guardrails chunk grows by 88 B gzip (within its budget); the page-load graph shrinks by 24 B.
- A cited card's button, and any other card button, that opens another origin in a new tab sends no referrer (`rel="noopener noreferrer"`), as a link in a remote reply already did. `openTarget()` opens a new tab with `noopener,noreferrer`.
- The model bench runs each case that doesn't `continues` another in a browser context of its own, so a handoff a `(Send)` case left open is no longer reopened from storage by the next, unrelated case. Lane A, which keeps one profile, clears the site's `localStorage` instead. A prompt is also sent as a remote turn when the page shows its handoff bar before it has recorded any handoff state.
